Bagian 1

Processor, Thread, Process & Context Switching

Membangun virtual processor di atas prosesor fisik serta biaya pergantian konteks.

Hierarki Konseptual

Sistem komputasi modern dibangun berdasarkan tiga tingkatan entitas prosesor:

Tingkat 1

Processor (Physical)

Perangkat keras fisik yang menyediakan sekumpulan instruksi dan mampu mengeksekusi instruksi tersebut secara otomatis.

Tingkat 2

Thread (Minimal Software)

Minimal software processor yang menjadi konteks eksekusi serangkaian instruksi. Memiliki execution context untuk menyimpan status jeda.

Tingkat 3

Process (Software Processor)

Software processor lengkap yang menjadi wadah tempat satu atau lebih thread dijalankan secara bersamaan dalam satu address space.

Tiga Jenis Context Switching

Context switching adalah proses menghentikan sementara eksekusi, menyimpan informasi statusnya, dan melanjutkan eksekusi entitas lain:

Jenis Context Informasi yang Disimpan Tingkat Bobot Komputasi
Processor Context Nilai minimal register prosesor (Program Counter, Stack Pointer, Addressing Registers). Sangat ringan.
Thread Context Processor context ditambah status (state) internal dari thread tersebut. Ringan (berbagi address space yang sama).
Process Context Thread context ditambah nilai register MMU (Memory Management Unit) dan tabel address space. Berat (memerlukan instruksi trap ke OS kernel dan pergantian ruang memori).
Biaya Context Switch: Direct vs Indirect Costs

Direct Costs: Biaya langsung eksekusi kode pergantian register dan instruksi interrupt handler.
Indirect Costs: Dampak terganggunya cache prosesor. Ketika proses berganti, isi cache memory terbuang (*cache thrashing*), sehingga proses yang baru mengalami *cache miss* beruntun dan performa melambat drastis.

Bagian 2

Implementasi Thread: User-Space vs Kernel-Space

Perdebatan mendasar: apakah thread dikelola package aplikasi atau langsung oleh kernel OS.

Aspek Analisis User-Space Threads Kernel-Space Threads
Pihak Pengelola Package library aplikasi di user space (tanpa campur tangan OS). Operating System Kernel langsung.
Kecepatan Switching Sangat cepat (dapat dilakukan murni di user space tanpa system call). Lebih lambat karena memerlukan *trap to kernel* (overhead system call).
Perilaku Saat Blocking Kelemahan Besar: Jika satu thread melakukan operasi I/O yang memblokir, seluruh proses ikut terhenti. Keunggulan: Ketika satu thread terblokir, kernel dapat langsung menjadwalkan thread lain dalam proses yang sama.
Penanganan Event Eksternal Kernel sulit membedakan dan mengarahkan sinyal ke thread tertentu. Kernel dapat dengan mudah menangkap sinyal dan meneruskannya ke thread spesifik.
Pendekatan Kombinasi (Two-Level Threading)

Menggabungkan keunggulan keduanya: sekelompok *user-level threads* dieksekusi di atas sejumlah *kernel threads*. Jika user thread melakukan blocking system call, kernel thread tersebut terblokir, tetapi kernel tetap dapat menjadwalkan kernel thread lain yang membawa user thread lain yang masih siap jalan (*runnable*).

Bagian 3

Threads dalam Sistem Terdistribusi

Penerapan thread pada klien untuk menyembunyikan latensi dan pada server untuk struktur yang bersih.

1. Client-Side: Multithreaded Web Client

Browser web memanfaatkan multithreading untuk mengambil aset (gambar, CSS, script) dari beberapa server secara bersamaan. Saat satu koneksi menunggu latensi jaringan, koneksi lain tetap mengunduh, sehingga browser dapat merender halaman secara bertahap tanpa macet.

Rumus Thread-Level Parallelism (TLP)

Mengukur rata-rata jumlah thread yang dieksekusi bersamaan ketika sistem aktif:
TLP = (Σ i × ci) / (1 - c0)
Catatan Ujian: Nilai TLP browser umumnya hanya berkisar antara 1.5 hingga 2.5. Artinya, thread pada browser lebih banyak berfungsi untuk mengorganisasikan aktivitas secara logis agar tidak blocking, bukan murni mengejar throughput paralel raksasa.

2. Server-Side: Dispatcher/Worker Model

Pola arsitektur standar server konkuren untuk menangani banyak request secara paralel:

Komponen 1

Dispatcher Thread

Bertugas terus menerus mendengarkan jaringan (*listen*), menerima request yang masuk dari klien, lalu membagikannya ke worker yang luang.

Komponen 2

Worker Threads

Sekumpulan thread pekerja independen yang menerima request dari dispatcher dan mengeksekusi logika pemrosesan secara paralel.

Model Organisasi Server Tingkat Paralelisme Gaya System Call
Multithreading Tinggi (Paralel nyata di multicore). Blocking system calls yang mudah dipahami.
Single-Threaded Process Tidak ada paralelisme. Blocking system calls (rentan bottleneck).
Finite-State Machine (FSM) Paralelisme event-driven. Nonblocking system calls (sangat efisien namun rumit).
Bagian 4

Prinsip Virtualisasi & Kontainer

Mekanisme meniru antarmuka (mimicking interfaces), syarat Popek-Goldberg, dan isolasi Linux Container.

Virtualisasi lahir karena perangkat keras berubah lebih cepat daripada perangkat lunak, serta kebutuhan akan portabilitas dan isolasi keamanan yang ketat.

Tipe Virtualisasi Level Antarmuka Karakteristik & Contoh
Process Virtual Machine Instruction set tersendiri di atas OS. Menggunakan interpreter/emulator (contoh: Java Virtual Machine / JVM).
Native VMM (Type 1 Hypervisor) Low-level instructions langsung di atas hardware. Berjalan langsung di atas bare-metal dengan minimal OS (contoh: VMware ESXi, KVM).
Hosted VMM (Type 2 Hypervisor) Low-level instructions di atas Host OS. Mendelegasikan sebagian besar tugas I/O ke full-fledged Host OS (contoh: VirtualBox, VMware Workstation).
Syarat Formal Popek-Goldberg untuk Virtualisasi

Sebuah VMM dapat dibangun secara efisien jika seluruh Sensitive Instructions (instruksi yang mengubah konfigurasi atau perilaku mesin) merupakan himpunan bagian dari Privileged Instructions (instruksi yang menyebabkan trap ke kernel jika dipanggil di user mode):
Sensitive Instructions ⊆ Privileged Instructions
Jika syarat ini dilanggar (seperti pada arsitektur x86 lama), solusinya adalah emulasi penuh, pembungkusan instruksi sensitif, atau Paravirtualization (memodifikasi kode kernel guest OS agar tidak memanggil instruksi sensitif terlarang).

Arsitektur Kontainer: Tiga Pilar Linux

Kontainer memberikan isolasi proses tanpa overhead menjalankan OS guest lengkap. Tiga mekanisme pondasinya:

  • Namespaces: Mengisolasi pandangan identifier sistem (Process ID, Network interface, Mount points, User IDs) sehingga proses di dalam kontainer merasa memiliki sistem sendiri.
  • Union File System (UnionFS): Menggabungkan beberapa lapisan image file system di mana hanya layer teratas yang dapat ditulisi (*read-write layer*).
  • Control Groups (cgroups): Membatasi dan mengukur alokasi sumber daya fisik (kuota persentase CPU, batas memori RAM, dan I/O bandwidth).
Bagian 5

Arsitektur Klien, Server & Server Clusters

Stateless vs Stateful, TCP Handoff pada cluster 3-tier, dan CDN request routing.

Karakteristik 1

Stateless Server

Tidak menyimpan informasi status klien setelah request selesai. Klien dan server independen. Jika server crash, pemulihan sangat mudah tanpa state yang rusak (contoh: HTTP murni).

Karakteristik 2

Stateful Server

Menyimpan status sesi klien (file yang sedang dibuka, cache klien). Memberikan performa sangat tinggi lewat *prefetching*, namun pemulihan saat crash menjadi jauh lebih rumit.

Server Cluster 3-Tier & TCP Handoff

Cluster server modern dibagi menjadi: First Tier (Logical Switch / Load Balancer), Second Tier (Application Compute Servers), dan Third Tier (Distributed Database).

Mekanisme TCP Handoff (Mencegah Bottleneck)

Jika seluruh lalu lintas bolak-balik harus melewati switch tier-1, switch tersebut akan segera kewalahan (*bottleneck*). Pada TCP Handoff: klien membuka koneksi dengan switch, switch menentukan server tier-2 terbaik, lalu koneksi TCP dialihkan (*handoff*) ke server tersebut. Selanjutnya, server tier-2 mengirimkan respons langsung ke klien tanpa membebani switch lagi!

Akamai CDN: Dynamic DNS Routing

Ketika klien meminta konten web, DNS khusus CDN mengembalikan alamat IP Edge Server terdekat. Jika konten ada di cache edge, konten langsung disajikan. Menariknya, CDN modern tidak hanya meng-cache file statis, tetapi juga dapat mengeksekusi sebagian kode aplikasi (*serverless/edge functions*) di edge server.

Bagian 6

Migrasi Kode (Code Mobility)

Memindahkan komputasi mendekati lokasi data untuk memangkas latensi dan menjaga privasi.

4 Alasan Utama Migrasi Kode

1. Load Distribution: Menyeimbangkan beban kerja di data center.
2. Minimizing Communication: Memindahkan kode kecil menuju server basis data raksasa, bukan menarik data bergiga-gita ke klien.
3. Flexibility: Mengunduh kode dinamis saat dibutuhkan tanpa instalasi manual.
4. Privacy and Security: Contoh nyata pada Federated Machine Learning: data medis pasien tidak boleh keluar dari rumah sakit, sehingga model/kode AI yang dikirim ke rumah sakit untuk dilatih secara lokal.

Weak Mobility vs Strong Mobility

Sebuah objek program terdiri dari: Code Segment (kode program), Data Segment (variabel/state data), dan Execution State (program counter, stack frame thread).

Aspek Pembeda Weak Mobility Strong Mobility
Segmen yang Dipindahkan Hanya Code Segment dan Data Segment. Code Segment, Data Segment, dan Execution State lengkap.
Kelanjutan Eksekusi Eksekusi dimulai dari awal (*reboot execution*). Eksekusi dilanjutkan tepat di titik saat jeda.
Mekanisme / Contoh Code Shipping (push ke tujuan) atau Code Fetching (pull unduh ke klien, seperti JavaScript di web). Process Migration (pindah utuh) atau Cloning (kloning proses identik).

3 Metode Migrasi Virtual Machine

Pushing Memory Pages

VM tetap berjalan di mesin asal sementara halaman memori dikirim secara bertahap. Halaman yang berubah (*dirty pages*) dikirim ulang secara iteratif.

Stop and Copy

VM dihentikan total, seluruh isi memori disalin ke mesin tujuan, lalu VM dinyalakan kembali. Menimbulkan *downtime* yang nyata.

Pulling Memory Pages

VM langsung dinyalakan di mesin tujuan, lalu mengambil halaman memori yang belum ada dari mesin asal secara *on-demand* saat dibutuhkan.

Bagian 7

Lembar Rangkuman Cepat (Exam Cheat Sheet)

Pembeda utama konsep proses, thread, virtualisasi, dan migrasi untuk soal ujian UTS.

Pasangan Konsep Pembeda Utama untuk Ujian
Process vs Thread Context Thread Context menyimpan register & state thread (berbagi memori) vs Process Context menyimpan register MMU & tabel memori terpisah.
Direct vs Indirect Switch Cost Biaya instruksi CPU & OS trap langsung vs Kerugian performa akibat hilangnya data cache prosesor (*cache miss*).
User-Space vs Kernel-Space Threads Switching cepat tanpa trap kernel tetapi rentan blocking proses total vs Switching dengan overhead trap tetapi satu blocking tidak mematikan thread lain.
Dispatcher vs Worker Menerima request jaringan & membagikan tugas vs Memproses logika komputasi tugas secara paralel.
Popek-Goldberg Condition Virtualisasi efisien terjamin jika Sensitive Instructions ⊆ Privileged Instructions.
Container: Namespaces vs cgroups Namespaces mengisolasi pandangan sistem (identifier) vs cgroups membatasi kuota kuantitatif sumber daya fisik (CPU/RAM).
Iterative vs Concurrent Server Menangani satu request sampai tuntas sebelum menerima request baru vs Menangani banyak request serentak melalui dispatcher-worker.
Stateless vs Stateful Server Bebas info klien, pemulihan crash mudah vs Menyimpan sesi klien, mendukung prefetching dan cache lokal berkinerja tinggi.
TCP Handoff Mengalihkan koneksi TCP langsung ke server pemroses agar switch tier-1 tidak menjadi bottleneck.
Weak vs Strong Mobility Pindah Code + Data (eksekusi reboot dari nol) vs Pindah Code + Data + Execution State (eksekusi lanjut mulus).
